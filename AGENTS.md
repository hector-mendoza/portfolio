# Agents.md

Rules for AI coding agents working in this repository. Read this file before making changes. Prefer the living product docs when making product or design decisions:

| Doc | Purpose |
| --- | --- |
| [PRD.md](./PRD.md) | What the product should do and which problems it solves |
| [DESIGN_SYSTEM.md](./DESIGN_SYSTEM.md) | Visual language, tokens, UI rules |
| [Architecture.md](./Architecture.md) | Technical systems and where changes belong |

---

## 1. Mission

Ship careful, reviewable changes that keep hectormendoza.me feeling like a product — performant, accessible, on-brand — not a template. Prefer small, intentional diffs over broad rewrites.

## 2. Behavior rules

1. **Read before write** — inspect neighboring components, tokens, and docs; match local patterns.
2. **Respect the Next.js docs block above** — do not assume App Router / config APIs from older major versions.
3. **One job per change** — do not mix drive-by refactors with feature work unless required for correctness.
4. **Preserve agent surfaces** — if bio, skills, projects, or contact facts change, update UI **and** `/api/agent` + `public/llms.txt` when those facts are public.
5. **Design-system first** — use CSS variables and glass utilities; do not invent a parallel palette.
6. **Motion is optional for users** — wire `usePrefersReducedMotion` (or equivalent) for ornamental animation.
7. **Do not break mobile** — watch `overflow-x`, bento `order-*`, and tap targets.
8. **No secrets in the repo** — use `.env.local` / example files; never commit tokens.
9. **Keep the Next.js agent block intact** — it is regenerated by `next dev`; do not delete the `BEGIN`/`END` markers.
10. **Tests when logic moves** — add or update Vitest coverage next to `lib/` helpers you change.

## 3. Allowed tools & workflows

Agents may use:

| Tooling | Typical use |
| --- | --- |
| Repo filesystem + git | Implement, commit on feature branches |
| `npm run dev` / `build` / `lint` / `test` | Verify locally |
| `npm run bones:build` | Refresh skeletons (needs running dev server) |
| Sanity Studio (`/studio` or `npm run sanity`) | Content schema validation — not for inventing fake production content |
| shadcn MCP (`.mcp.json`) | Component registry workflows when relevant |
| GitHub CLI (read) | Inspect PRs, CI logs |
| Browser / Playwright MCP | Visual verification of UI changes |

Do **not**:

- Deploy production, rotate credentials, or mutate remote Sanity datasets without explicit human instruction
- Rewrite `AGENTS.md` Next.js markers as a “cleanup”
- Introduce new heavy dependencies when an existing primitive covers the need

## 5. Definition of done

A change is ready when:

- [ ] It matches PRD intent and Architecture boundaries
- [ ] UI follows Design System tokens and composition rules
- [ ] `npm run lint` and `npm test` pass for touched concerns
- [ ] Agent/public profile surfaces are still accurate if facts changed
- [ ] Mobile and reduced-motion paths were considered for UI work

## 6. Communication

- Prefer concise PR descriptions: problem → approach → verification.
- Call out intentional visual deltas (theme, motion, hero composition).
- If blocked by missing Sanity credentials, note that home can still be verified without them.
